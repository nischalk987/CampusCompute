# CampusCompute Local API

The FastAPI service is an optional local-development adapter. It runs on the same Ubuntu/WSL machine as the C executables and exposes fixed operations rather than a general-purpose shell.

## Requirements and setup

Use Ubuntu or WSL Ubuntu with Python 3, venv, pip, GCC and GNU Make. From the repository root:

```bash
sudo apt update
sudo apt install -y build-essential python3 python3-venv python3-pip
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
```

Start the API from the repository root:

```bash
uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

- Health: http://127.0.0.1:8000/health
- Module capability inventory: http://127.0.0.1:8000/api/modules
- Interactive API documentation: http://127.0.0.1:8000/docs

Keep the server bound to `127.0.0.1`. Do not expose this development adapter to the public internet.

## Current API operations

| Method and route | Purpose |
|---|---|
| `GET /health` | Service health and engine capability metadata |
| `GET /api/modules` | Module/API capability inventory |
| `POST /api/producer-consumer?event_count=N` | Run the real FR3 C executable and return parsed log events |
| `POST /api/terminal/session/start` | Start an allowlisted repository executable in a local PTY session |
| `POST /api/terminal/session/input` | Send input to an existing local PTY session |
| `GET /api/terminal/session/{session_id}` | Poll output and process state |
| `DELETE /api/terminal/session/{session_id}` | Stop and clean up a PTY session |
| `POST /api/terminal/execute` | Run a restricted local development command |

### Producer–consumer request

`event_count` is an integer from 1 through 100000. Example:

```bash
curl -X POST "http://127.0.0.1:8000/api/producer-consumer?event_count=3"
```

The response contains `status`, `source`, `event_count_requested`, `events_produced`, `events`, and `summary`. Event timestamps and messages are generated by the C program at runtime.

## Feature boundary

- FR1 job manager: implemented in C; no structured HTTP CRUD/list API.
- FR2 scheduler: implemented in C; no structured scheduling API.
- FR3 producer–consumer: implemented in C and exposed through the structured endpoint above.
- FR4 shared-memory IPC: implemented in C and integrated CLI; no structured HTTP endpoint.
- FR5 Banker's Algorithm: implemented in C; no structured HTTP endpoint.
- FR6 process manager: implemented in C and integrated CLI; no structured HTTP endpoint.
- FR7 resource limits: implemented in C and integrated CLI; no structured HTTP endpoint.
- FR8 integrated CLI: implemented in C; not replaced by the dashboard.

The module inventory endpoint is a runtime capability response. Consult the C CLI and this documented boundary rather than assuming every dashboard view is API-backed.

## Errors and lifecycle

| Condition | HTTP status | Behavior |
|---|---:|---|
| Invalid or out-of-range producer event count | 422 | Reject request validation |
| C build or executable unavailable | 503 | Return build/tooling error |
| C operation exceeds execution deadline | 504 | Report timeout |
| C process returns non-zero | 422 | Return bounded process detail |
| Missing or malformed generated log | 502 | Reject inconsistent output |
| Filesystem/read failure | 500 | Report log processing failure |

The producer endpoint uses a temporary directory for its activity log and removes it after processing the response.

## Local terminal safety

The terminal API is intentionally restricted:
- It is intended only for the local CampusCompute dashboard and checks the request origin.
- Commands are parsed into argument arrays; shell operators and shell expansion are rejected.
- The executable and working directory must remain inside the repository.
- Interactive sessions are limited and have explicit start, input, poll and stop operations.
- The service should remain bound to localhost.

Do not treat this as a public shell service. Do not expose the API through a public interface or reverse proxy.

## Dashboard

In a second terminal, from the repository root:

```bash
cd frontend
npm install
npm run dev
```

Open the Vite URL printed in the terminal. The dashboard and backend are separate processes; keep both running while testing API-connected views.

## Tests

From the repository root with the virtual environment activated:

```bash
PYTHONPATH=backend pytest -q backend/tests
```

Or run `make test-backend`. The tests cover the FR3 execution adapter, request validation, unavailable engine, timeout/error handling, malformed logs, capability reporting and terminal restrictions.
